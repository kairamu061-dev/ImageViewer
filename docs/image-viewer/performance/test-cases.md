## 実施記録

- 2026-10-10: ユーザ実機確認。E-01（「画像がありません」再発確認）は不合格 — LRU化・リトライ後も再発。原因未解決のため `_load_qimage`/`_load_thumb`/`show_image` にログ出力を追加（E-04）
- 2026-10-10: ユーザからログ提供。同一ファイルへの読み込み試行が約750ms〜1秒近く連続して失敗していることを確認（E-04 合格）。即時リトライでは不十分と判断し、300ms/1000ms/3000msのバックオフ付き遅延リトライを実装（E-05）。再確認待ち
- 2026-10-10: ユーザ実機再確認 — 遅延リトライ後も「変わってなかった」。2回目のログでも同様に1秒以上の連続失敗を確認。プリロードの並列読み込みによるドライブへのスラッシングを追加原因と推定し、ImageCache 専用プール（並列度2）とリトライ間隔延長（500/1500/4000/9000ms）を実施。再確認待ち
- 2026-10-10: ユーザに確認し D: ドライブが内蔵HDDと判明。HDDはランダムな同時シークに弱いため、ImageCache 専用プールを並列度2→1（完全直列）に変更。再確認待ち
- 2026-10-10: ユーザ実機再確認（3回目）— 完全直列化後も「直ってない」（E-05 不合格）。ユーザの指摘（キャッシュしか見ていないのでは）を受けて遅延リトライの実装を再点検し、`_retry_show_image` がページ送りの度に進行中のリトライを毎回キャンセルしていた実装バグを発見。遅延リトライが実質一度も完走していなかった可能性が高い。中断条件をフォルダ変更時のみに修正（E-06 追加）。再確認待ち
- 2026-10-10: ユーザ実機再確認（4回目）— ログで "giving up after retries" を確認。今回はリトライが中断されず最後まで完走した上での失敗と判明（E-06 合格）。ユーザから「一覧表示では同じファイルが表示できている」という決定的な情報を得て、成功する `_load_thumb` と失敗する `_load_qimage` を比較し、`read()` 前の `reader.size()` 呼び出しの有無が唯一の差分と判明。`_load_qimage` にも追加（E-07）。再確認待ち
- 2026-10-10: ユーザ実機再確認（5回目）— `size()` 追加後も解消せず（E-07 不合格）。ログが毎回同じファイル・同じエラーで100%再現することから、問題を「一過性の外部ブロック」ではなく「フル解像度デコードが決定的に失敗する」現象に認識を修正。`_load_qimage` に「元のサイズのまま `setScaledSize` 経路を使うフォールバック」を追加し、効果のなかった `get_sync` の即時リトライは削除（E-08 追加）。再確認待ち
- 2026-10-10: ユーザ実機再確認（6回目）— ログで "scaled-fallback decode also failed" を確認、1:1指定のフォールバックも解消せず（E-08 不合格）。元サイズ指定では実際のDCTスケーリングが発生しないため無効と判断し、`_FALLBACK_SCALES`（7/8→1/2→1/4）による段階的縮小カスケードに変更。最終手段として一覧表示と同じ384px（これまで一度も失敗していない設定）まで用意（E-09 追加）。再確認待ち
