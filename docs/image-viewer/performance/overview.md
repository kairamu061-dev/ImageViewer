# performance 概要

## 目的・背景

ユーザーから報告された2つの性能問題と、それに関連する不具合1件に対処する機能グループ。

- 不具合: 画像ファイルが多いフォルダで、1枚表示にすると一部の画像が「画像がありません」と表示される（一覧表示では正しく表示される。発生する画像は毎回同じではなく、再現性が不安定）
- 要望: フォルダビューで多数のフォルダが開かれる（展開・スクロールされる）際の処理が重い
- 要望: 一覧表示（サムネイルグリッド）でスクロールする際の処理が重い

調査の結果、3つとも「画像デコード系の処理が `QThreadPool.globalInstance()` を無制限に共有している」ことに起因する、同じ根本原因の異なる現れ方だと判断した。

- `ImageCache`（1枚表示のキャッシュ）はフォルダ内を巡回するほど全解像度の `QPixmap` を無制限に溜め込み、大きいフォルダで長く閲覧するとメモリを圧迫し、デコードが一時的に失敗することがある（一覧表示は縮小デコードのみなので影響を受けない）
- `FolderOnlyModel`（フォルダツリー）は展開された全フォルダに対して即座に非同期チェックを投げ、画像デコードと同じプールを奪い合う
- `ThumbnailGridView`（一覧表示）はフォルダを開いた瞬間に全画像分のサムネイル読み込みを一括でキューに積み、スクロール中もそれらが終わるまで競合し続ける

## スコープ

### 作るもの

- `ImageCache` にLRU方式のキャッシュ上限を設け、無制限なメモリ増加を防ぐ
- 画像読み込み失敗時の1回リトライ（一時的なI/O失敗への耐性）
- フォルダツリーのサブフォルダ存在チェック用に専用の小さいスレッドプールを用意し、画像デコードと競合しないようにする
- 一覧表示のサムネイル読み込みを「表示範囲＋バッファ」に限定し、スクロールに応じて追加読み込みする方式に変更
- 一覧表示にも専用のスレッドプールを用意する

### 作らないもの

- サムネイルのディスクキャッシュ（永続化）
- フォルダツリーの仮想化（表示行数を絞る等の抜本的な再設計）
- プログレスバー等の読み込み状況UI

## 制約

- 既存のAPI（`ImageViewerPanel`, `ThumbnailGridView`, `FolderOnlyModel` の外部インターフェース）は変更しない
- この開発環境には Python/PyQt6 実行環境がなく、実機（Windows）でのユーザー確認に依存する

## 完了条件

- 画像ファイルが多いフォルダを長時間閲覧しても「画像がありません」が再発しない
- 多数のフォルダを開いても操作が重く感じない
- 一覧表示でのスクロールが重く感じない
