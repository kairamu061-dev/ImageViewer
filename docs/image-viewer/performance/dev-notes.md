# performance 開発メモ

## 「画像がありません」不具合: 確定した原因と最終対処（要約）

- **原因**: 問題のJPEGファイルはフル解像度(1:1)デコードのみ決定的に失敗する（ファイル末尾付近の軽微な破損を、素の `read()` は読み切れない）。実際に縮小するデコード（libjpegのDCTスケーリング）なら 7/8 でも通過できる。一覧表示が当初から正常だったのは常に縮小デコードを使っていたため。
- **最終対処**: `image_cache._load_qimage()` で素の `read()` が失敗したら、7/8→1/2→1/4→384px縮小 と段階的に実縮小したデコードを試す（`scaled-fallback decode succeeded at 88%` で解消を実機確認）。
- **効果のなかった対処（後学のため）**: LRU上限・スレッドプール分離/直列化・遅延リトライ・`size()`先行呼び出し・1:1の`setScaledSize`は、いずれも「一過性・環境要因」という誤った前提に基づくもので、この不具合の解決には寄与しなかった（性能面の改善としては維持）。決め手は「実機ログの採取」と「一覧表示との唯一の本質的差分＝縮小デコードか否か」の特定だった。

## 実装上の判断

| 判断内容 | 理由 |
|----------|------|
| 「画像がありません」不具合の根本原因をメモリ圧迫による一過性デコード失敗と推定 | ユーザ報告の特徴（画像ファイルが多いフォルダ限定、毎回同じ画像ではない、一覧表示では再現しない、日をおくと直る）が、1枚表示用キャッシュ（全解像度・無制限）と一覧表示用サムネイル（縮小・そもそも影響を受けない）の違いときれいに一致するため。実機での確証はないが、対策（LRU化・リトライ）自体は副作用がなく妥当な改善なので採用 |
| CACHE_LIMIT を 60 に設定 | PRELOAD_RADIUS（前後3枚）に対して十分余裕があり、通常の前後移動では破棄・再読込が起きない一方、無制限成長は確実に防げる値として設定。厳密な計測はしていないため将来チューニングの余地あり |
| 3つのサブシステム（ImageCache・FolderOnlyModel・ThumbnailGridView）全てが `QThreadPool.globalInstance()` を共有していたことを「重さ」の共通原因と判断 | 大量のフォルダ展開（フォルダツリー）・大量サムネイル読み込み（一覧表示）・画像プリロード（1枚表示）が同じ限られたスレッド数を奪い合うと、個別には軽い処理でも全体として重くなる。サブシステムごとに専用プールへ分離することで、一方の大量処理が他方を飢餓状態にしないようにした |
| 一覧表示の可視範囲判定に `indexAt()` を使用 | グリッドの列数・セルサイズ・スクロール位置から自前で行範囲を計算するより、Qt自身のレイアウト結果をそのまま問い合わせる方が正確でバグが入りにくいため |
| 「画像がありません」不具合の対策を、即時リトライではなく指数的バックオフ（300ms/1000ms/3000ms）の遅延リトライに変更 | 実機ログで同一ファイルが約750ms〜1秒近くの間、間を置かず何度試しても毎回同じ "Unable to read image data" で失敗し続けていることを確認（get_sync 内の即時リトライも効かなかった）。これは一瞬のグリッチではなく外部要因（アンチウイルスのスキャン、クラウド同期のロック等）による一定時間のブロックだと判断し、時間を置いて回復を待つ方式にした |
| 遅延リトライの判定に `folder` と `index` の両方を使用 | タイマー発火時に別フォルダへ切り替わっていても偶然同じ数値インデックスだと誤って上書きしてしまうため、フォルダの一致も確認してから反映する |
| `ImageCache` にも専用の小さいスレッドプール（`maxThreadCount=2`）を追加 | 2回目のユーザログで、同じファイルへの読み込み失敗が約1秒以上続く状況が再確認され、遅延リトライ（300/1000/3000ms）でも解消しなかった。プリロード（前後3枚＝最大7件）が `QThreadPool.globalInstance()` の既定並列度で同時に同じドライブへランダムアクセスしていたことが、低速ドライブ（HDD/ネットワークドライブ等）でのスラッシング（読み込み競合による遅延・失敗）を招いていた可能性が高いと判断し、並列度を絞って同時アクセス数を減らした |
| 遅延リトライの間隔を 500/1500/4000/9000ms（計4回）に延長 | 実機ログで数秒単位の連続失敗が確認されたため、以前の 300/1000/3000ms（計約4.3秒）では不十分と判断し余裕を持たせた |
| ImageCache の並列度を2→1（完全直列）に変更 | ユーザに確認したところ D: ドライブは内蔵HDDと判明。HDDはSSDと異なりランダムな同時シークに弱く、2並列でもまだ競合が起きうるため、プリロードは1枚ずつ順番に読む完全直列に変更した。現在表示中の画像の読み込み（`get_sync`、メインスレッド）はこのプールの外なので、最悪でも「直列プリロード1件＋表示中の読み込み1件」の2件同時までに抑えられる |
| 並列度を1→2 に戻した（真因判明後） | 不具合の真因はデコード側（フル解像度デコードの決定的失敗）でありドライブ競合ではなかったと確定したため、完全直列は過剰と判断。他プールとの分離目的は維持しつつ、先読みが遅くなる副作用を避けるため2に戻した。LRU上限・スレッドプール分離は性能面の改善として維持 |
| `_retry_show_image` の中断条件から「現在表示中のインデックスと一致するか」を外した | ユーザ指摘で発覚: ページ送りで別の画像に移動した瞬間、まだ結果の出ていない遅延リトライが毎回黙ってキャンセルされていた。通常の読書（連続ページ送り）では最短500msの初回リトライすら完走せず、実質的に遅延リトライが一度も機能していなかった。フォルダが変わった場合のみ中断し、ページ送りでは継続してバックグラウンドで再試行し続け、成功したらキャッシュに格納（表示中ならキャンバスも更新）するよう変更 |
| `_load_qimage` に `reader.size()` の呼び出しを追加（`read()` の前） | リトライを最後まで完走させても解消しなかったことに加え、ユーザから「一覧表示（サムネイル）では同じファイルが問題なく表示できている」という決定的な情報を得た。一覧表示側の `_load_thumb` は `read()` の前に必ず `reader.size()` を呼んでいるが、1枚表示側の `_load_qimage` は呼んでいなかった唯一の実装差分。ファイル自体は壊れておらずQtで読めることが確定したため、`size()` 先行呼び出しの有無がこの不具合の実際の原因である可能性が高いと判断し追加 |
| **問題の性質を「一過性の外部ブロック」から「特定ファイルのフル解像度デコードが決定的に失敗する」に認識を修正** | `size()` 追加後も実機確認で解消せず、ログで毎回同じファイル・同じエラーで、リトライ回数やタイミングに関わらず100%再現することを確認。これは一過性のグリッチでは説明できず、このファイル固有の決定的な現象と判断。一覧表示（`_load_thumb`、縮小デコード=`setScaledSize`使用）は常に成功し、1枚表示（`_load_qimage`、フル解像度の素の`read()`）は常に失敗する、という組み合わせから、縮小デコード経路（libjpegのDCTスケーリング）だけが特定の軽微な破損／異常を許容できている可能性が高いと推定 |
| `_load_qimage` に「フル解像度のまま`setScaledSize`経路を使うフォールバック」を追加、`get_sync`の外側リトライは削除 | 上記の認識修正に基づく対策。素の`read()`が失敗したら、`reader.size()`で取得した**元のサイズをそのまま`setScaledSize`に設定**して再読み込みする（画質は落とさず、縮小デコードと同じ経路を使うだけ）。失敗が決定的である以上、`get_sync`側の単純な2回目の`_load_qimage`呼び出し（内容が同じ処理の繰り返し）は意味がないため削除し、ログの重複も解消した |
| `setScaledSize`を元サイズ(1:1)で指定するフォールバックは無効と判明 → 段階的に縮小率を上げるカスケード方式に変更 | 実機確認で、元サイズのまま`setScaledSize`を指定しても同じエラーで失敗することが判明。1:1指定では実際のlibjpeg DCTスケーリングが発生せず、素の`read()`と実質同じフル精度デコードになってしまうため効果がなかったと判断。7/8→1/2→1/4と段階的に本当に縮小していくフォールバックに変更し、最終手段として一覧表示と全く同じ384px縮小（これまで一度も失敗していない設定）を試すようにした。これにより理論上は必ずどこかの段階で成功する |

## 発生した問題と対処

| 問題 | 対処 |
|------|------|
| （不具合）画像ファイルが多いフォルダで1枚表示の一部画像が「画像がありません」になる。一覧表示では発生しない。再現する画像が毎回異なり、日をおくと直ることもある（ユーザ報告） | 当初 `ImageCache._cache` の無制限growth（メモリ圧迫）が原因と推定し、LRU化（`CACHE_LIMIT=60`）とリトライを実装したが、ユーザ実機で再現が継続しこの仮説は外れたことが判明。ログから同一ファイルへの複数回の読み込み試行が約750ms〜1秒近く連続して失敗していることを特定し、`ImageViewerPanel` にバックオフ付き遅延リトライを追加 → 変化なし。HDD確認を受けて `ImageCache` の並列度を1（完全直列）に変更 → それでも変化なし（3回目の確認）。ユーザからの「そもそもキャッシュしか見てないのでは」という指摘を受けて遅延リトライの実装を再確認したところ、`_retry_show_image` が「表示中のインデックスと一致するか」を中断条件にしており、ページ送りする度に進行中のリトライを黙ってキャンセルしていた実装バグを発見・修正 → それでも4回目の確認で解消せず、今回はリトライが最後まで完走（"giving up after retries" ログを確認）した上での失敗だった。ユーザから「一覧表示では同じファイルが問題なく表示できている」という決定的な情報を得て、`_load_thumb`（一覧表示、成功する）と `_load_qimage`（1枚表示、失敗する）の実装差分を比較し、まず `size()` 先行呼び出しを追加 → 5回目の確認でも解消せず。ログの再現性（毎回同じファイル・同じエラーで100%失敗）から問題の性質を「一過性の外部ブロック」ではなく「フル解像度デコードが決定的に失敗する」に認識を修正し、`_load_qimage` に「元のサイズのまま`setScaledSize`経路を使うフォールバック」を追加 → 6回目の確認で、これも同じエラーで失敗することが判明（ログで "scaled-fallback decode also failed" を確認）。元サイズ指定(1:1)では実際のDCTスケーリングが発生せず無意味だったと判断し、7/8→1/2→1/4と段階的に縮小するカスケード方式に変更。最終手段として一覧表示と全く同じ384px縮小（これまで一度も失敗していない設定）まで用意した。再確認待ち |
| （要望）フォルダビューで多数のフォルダが開かれる際の処理が重い | `FolderOnlyModel` のサブフォルダ存在チェック（`_DirCheckRunnable`）が `QThreadPool.globalInstance()` を使っており、画像デコード処理と競合していた。専用の小さいプール（`maxThreadCount=2`）に分離 |
| （要望）一覧表示でスクロールする際の処理が重い | `ThumbnailGridView._start_loading()` がフォルダを開いた瞬間に全画像分のサムネイル読み込みを一括でキューに積んでいた（dev-notes の「今後の課題」に記載していた既知の課題）。`_ensure_visible_loaded()` に変更し、可視範囲＋前後バッファ（`COLUMNS × PRELOAD_ROWS` = 10件）のみを読み込み、スクロールに応じて追加読み込みする方式に変更。専用スレッドプールも用意した |

## 設計からの変更点

なし（既存コンポーネントの内部実装のみの変更で、外部インターフェースは変更していない）

## 今後の課題

- CACHE_LIMIT（60）は実測に基づくチューニングをしていない。性能面の改善として維持するが、「画像がありません」不具合の対策としては効果が確認できなかった
- 「画像がありません」不具合はまだ原因未確定。ログ（`%TEMP%\ImageViewer.log`）の内容を見て、デコード失敗なのか・インデックスのずれなのか・例外なのかを特定する必要がある
- サムネイルのディスクキャッシュ永続化は未対応（タブ切り替え・再起動で再デコードが発生する）

## ユーザへの要望

- 実機（Windows）で、フォルダツリーの多数フォルダ展開・一覧表示のスクロールが軽くなったかを確認してほしい
- 「画像がありません」が再発した際は、`%TEMP%\ImageViewer.log`（例: `C:\Users\<ユーザー名>\AppData\Local\Temp\ImageViewer.log`）を確認し、その時間帯のログ内容を共有してほしい
