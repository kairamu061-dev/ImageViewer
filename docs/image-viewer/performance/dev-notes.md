# performance 開発メモ

## 実装上の判断

| 判断内容 | 理由 |
|----------|------|
| 「画像がありません」不具合の根本原因をメモリ圧迫による一過性デコード失敗と推定 | ユーザ報告の特徴（画像ファイルが多いフォルダ限定、毎回同じ画像ではない、一覧表示では再現しない、日をおくと直る）が、1枚表示用キャッシュ（全解像度・無制限）と一覧表示用サムネイル（縮小・そもそも影響を受けない）の違いときれいに一致するため。実機での確証はないが、対策（LRU化・リトライ）自体は副作用がなく妥当な改善なので採用 |
| CACHE_LIMIT を 60 に設定 | PRELOAD_RADIUS（前後3枚）に対して十分余裕があり、通常の前後移動では破棄・再読込が起きない一方、無制限成長は確実に防げる値として設定。厳密な計測はしていないため将来チューニングの余地あり |
| 3つのサブシステム（ImageCache・FolderOnlyModel・ThumbnailGridView）全てが `QThreadPool.globalInstance()` を共有していたことを「重さ」の共通原因と判断 | 大量のフォルダ展開（フォルダツリー）・大量サムネイル読み込み（一覧表示）・画像プリロード（1枚表示）が同じ限られたスレッド数を奪い合うと、個別には軽い処理でも全体として重くなる。サブシステムごとに専用プールへ分離することで、一方の大量処理が他方を飢餓状態にしないようにした |
| 一覧表示の可視範囲判定に `indexAt()` を使用 | グリッドの列数・セルサイズ・スクロール位置から自前で行範囲を計算するより、Qt自身のレイアウト結果をそのまま問い合わせる方が正確でバグが入りにくいため |
| 「画像がありません」不具合の対策を、即時リトライではなく指数的バックオフ（300ms/1000ms/3000ms）の遅延リトライに変更 | 実機ログで同一ファイルが約750ms〜1秒近くの間、間を置かず何度試しても毎回同じ "Unable to read image data" で失敗し続けていることを確認（get_sync 内の即時リトライも効かなかった）。これは一瞬のグリッチではなく外部要因（アンチウイルスのスキャン、クラウド同期のロック等）による一定時間のブロックだと判断し、時間を置いて回復を待つ方式にした |
| 遅延リトライの判定に `folder` と `index` の両方を使用 | タイマー発火時に別フォルダへ切り替わっていても偶然同じ数値インデックスだと誤って上書きしてしまうため、フォルダの一致も確認してから反映する |
| `ImageCache` にも専用の小さいスレッドプール（`maxThreadCount=2`）を追加 | 2回目のユーザログで、同じファイルへの読み込み失敗が約1秒以上続く状況が再確認され、遅延リトライ（300/1000/3000ms）でも解消しなかった。プリロード（前後3枚＝最大7件）が `QThreadPool.globalInstance()` の既定並列度で同時に同じドライブへランダムアクセスしていたことが、低速ドライブ（HDD/ネットワークドライブ等）でのスラッシング（読み込み競合による遅延・失敗）を招いていた可能性が高いと判断し、並列度を絞って同時アクセス数を減らした |
| 遅延リトライの間隔を 500/1500/4000/9000ms（計4回）に延長 | 実機ログで数秒単位の連続失敗が確認されたため、以前の 300/1000/3000ms（計約4.3秒）では不十分と判断し余裕を持たせた |
| ImageCache の並列度を2→1（完全直列）に変更 | ユーザに確認したところ D: ドライブは内蔵HDDと判明。HDDはSSDと異なりランダムな同時シークに弱く、2並列でもまだ競合が起きうるため、プリロードは1枚ずつ順番に読む完全直列に変更した。現在表示中の画像の読み込み（`get_sync`、メインスレッド）はこのプールの外なので、最悪でも「直列プリロード1件＋表示中の読み込み1件」の2件同時までに抑えられる |

## 発生した問題と対処

| 問題 | 対処 |
|------|------|
| （不具合）画像ファイルが多いフォルダで1枚表示の一部画像が「画像がありません」になる。一覧表示では発生しない。再現する画像が毎回異なり、日をおくと直ることもある（ユーザ報告） | 当初 `ImageCache._cache` の無制限growth（メモリ圧迫）が原因と推定し、LRU化（`CACHE_LIMIT=60`）とリトライを実装したが、ユーザ実機で再現が継続しこの仮説は外れたことが判明。`_load_qimage`等にログ出力を追加して再発時のログを採取したところ、同一ファイルへの複数回の読み込み試行（プリロード由来のものを含む）が約750ms〜1秒近く連続して "Unable to read image data" で失敗していることが判明。`get_sync` 内の即時リトライでは短すぎて無意味だったため、`ImageViewerPanel` 側に 300ms/1000ms/3000ms のバックオフ付き遅延リトライを追加したが、**2回目のユーザ確認でも変化なし**。2回目のログでも同様に約1秒以上の連続失敗を確認。プリロードがスレッドプールの既定並列度（CPUコア数程度）で同時に同じドライブへランダムアクセスしていたことがスラッシングの原因と推定し、`ImageCache` 専用プールの並列度を2に制限、遅延リトライの間隔も 500/1500/4000/9000ms に延長した。再確認待ち |
| （要望）フォルダビューで多数のフォルダが開かれる際の処理が重い | `FolderOnlyModel` のサブフォルダ存在チェック（`_DirCheckRunnable`）が `QThreadPool.globalInstance()` を使っており、画像デコード処理と競合していた。専用の小さいプール（`maxThreadCount=2`）に分離 |
| （要望）一覧表示でスクロールする際の処理が重い | `ThumbnailGridView._start_loading()` がフォルダを開いた瞬間に全画像分のサムネイル読み込みを一括でキューに積んでいた（dev-notes の「今後の課題」に記載していた既知の課題）。`_ensure_visible_loaded()` に変更し、可視範囲＋前後バッファ（`COLUMNS × PRELOAD_ROWS` = 10件）のみを読み込み、スクロールに応じて追加読み込みする方式に変更。専用スレッドプールも用意した |

## 設計からの変更点

なし（既存コンポーネントの内部実装のみの変更で、外部インターフェースは変更していない）

## 今後の課題

- CACHE_LIMIT（60）は実測に基づくチューニングをしていない。性能面の改善として維持するが、「画像がありません」不具合の対策としては効果が確認できなかった
- 「画像がありません」不具合はまだ原因未確定。ログ（`%TEMP%\ImageViewer.log`）の内容を見て、デコード失敗なのか・インデックスのずれなのか・例外なのかを特定する必要がある
- サムネイルのディスクキャッシュ永続化は未対応（タブ切り替え・再起動で再デコードが発生する）

## ユーザへの要望

- 実機（Windows）で、フォルダツリーの多数フォルダ展開・一覧表示のスクロールが軽くなったかを確認してほしい
- 「画像がありません」が再発した際は、`%TEMP%\ImageViewer.log`（例: `C:\Users\<ユーザー名>\AppData\Local\Temp\ImageViewer.log`）を確認し、その時間帯のログ内容を共有してほしい
