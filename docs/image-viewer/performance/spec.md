# performance 仕様

## 機能一覧

| # | 機能名 | 説明 |
|---|--------|------|
| 1 | ImageCache のLRU上限 | 1枚表示用キャッシュを最大件数で制限し、超えたら最も使われていないものから破棄 |
| 2 | ~~読み込み失敗時のリトライ~~（廃止） | `get_sync` での即時リトライは、失敗が決定的（毎回同じ結果）であることが判明したため効果がなく、重複ログの原因にしかならないため削除した |
| 3 | フォルダツリー専用スレッドプール | サブフォルダ存在チェックを専用の小さいプールで実行し、画像デコードと競合しないようにする |
| 4 | 一覧表示の可視範囲優先読み込み | サムネイル読み込みを「表示中の行＋前後バッファ」に限定し、スクロールに応じて追加読み込み |
| 5 | 一覧表示専用スレッドプール | サムネイル読み込みを専用プールで実行し、1枚表示のプリロードと競合しないようにする |
| 6 | 診断用ログ出力 | デコード失敗時にQtのエラー内容・例外を `%TEMP%\ImageViewer.log` に記録する |
| 7 | 1枚表示の遅延バックオフリトライ | デコード失敗時、500ms/1500ms/4000ms/9000msと間隔を空けて最大4回まで自動的に再表示を試みる |
| 8 | ImageCache 専用スレッドプール（低並列） | プリロードを専用プール（最大2並列）で実行し、グリッド/フォルダツリーのプールと競合させない。※一時的に完全直列(1)にしたが、不具合がデコード側の問題と判明したため2に戻した |
| 9 | ~~フル解像度(1:1)スケールデコード・フォールバック~~（無効と判明） | 元サイズのまま `setScaledSize` を指定しても実際の縮小が発生せず無意味だった |
| 10 | `_load_qimage` の段階的縮小カスケード・フォールバック | 素の `read()` が失敗した場合、7/8→1/2→1/4と段階的に縮小して再読み込みし、最終手段として一覧表示と同じ384px縮小（常に成功する設定）まで試す |

## 各機能の詳細

### ImageCache のLRU上限
- `ImageCache._cache` を `dict` から `collections.OrderedDict` に変更
- 上限 `CACHE_LIMIT = 60`。挿入時に上限を超えたら `popitem(last=False)` で最も古い（最も使われていない）エントリから破棄
- `get()` / `get_sync()` でキャッシュヒット時は `move_to_end()` し、直近アクセスしたものが破棄されにくくする

### 読み込み失敗時のリトライ
- `get_sync()` で `_load_qimage()` が `None` を返した場合、即座にもう1回だけ再試行する
- アンチウイルスやクラウド同期によるファイルの一時ロックなど、一過性のI/O失敗を想定した対策

### フォルダツリー専用スレッドプール
- `FolderOnlyModel._pool` を `QThreadPool.globalInstance()` から専用の `QThreadPool()`（`setMaxThreadCount(2)`）に変更
- 多数のフォルダを展開・スクロールしても、1枚表示や一覧表示のデコード処理を妨げない

### 一覧表示の可視範囲優先読み込み
- `ThumbnailGridView._ensure_visible_loaded()` が現在のビューポートに表示されている行範囲（`indexAt()` で算出）の前後 `COLUMNS × PRELOAD_ROWS`（= 5×2 = 10件）を読み込み対象とする
- 読み込み済み・読み込み指示済みのインデックスは `_dispatched` セットで管理し、重複ディスパッチしない
- `set_images()` / `showEvent()` / `resizeEvent()` / `scrollContentsBy()` の各タイミングで呼び出し、スクロールするたびに新しく見えてきた範囲を追加で読み込む

### 一覧表示専用スレッドプール
- `ThumbnailGridView._pool` を `QThreadPool.globalInstance()` から専用の `QThreadPool()` に変更

### 診断用ログ出力
- `main.py` の `_setup_logging()` で `logging.basicConfig` をファイル出力に設定（`%TEMP%\ImageViewer.log`）。ウィンドウアプリ（`console=False`）でコンソールが無いため
- `_load_qimage` / `_load_thumb` はデコード失敗時に `QImageReader.errorString()` を、例外発生時はスタックトレースをログに記録する（従来は無言で `None` を返すのみだった）

### 1枚表示の遅延バックオフリトライ
- `ImageViewerPanel.show_image()` で `get_sync()` が `None` を返した場合、`_schedule_retry()` で 500ms後に再試行をスケジュールする
- 失敗したら 1500ms後、4000ms後、9000ms後と間隔を空けて最大4回まで再試行する（`_RETRY_DELAYS_MS`）
- 再試行は表示中のフォルダが変わった場合のみ中断する。ページ送りで別の画像に移動しても、バックグラウンドでの再試行自体は継続する（通常の連続ページ送りでは最短500msの初回リトライすら完走しないため、ページ送りでの中断は行わない）
- 再試行が成功したら結果をキャッシュに格納する。その時点でユーザーがまだ（または再び）同じ画像を表示中であれば、操作なしに自動的に正しい画像に更新される

### ImageCache 専用スレッドプール（低並列）
- `ImageCache._pool` を `QThreadPool.globalInstance()` から専用の `QThreadPool()`（`setMaxThreadCount(2)`）に変更
- 「画像がありません」不具合の調査中に一時的に完全直列(1)にしたが、不具合の真因はデコード側（フル解像度デコードの失敗）と判明したため、2並列に戻した
- 他サブシステム（グリッド・フォルダツリー）のプールと分離する目的は維持
- 現在表示中の画像の読み込み（`get_sync`、メインスレッド）はこのプールの外で動くため、最悪でも「直列プリロード1件＋表示中の読み込み1件」の2件同時まで

### `_load_qimage` の段階的縮小カスケード・フォールバック
- ログの再現性（毎回同じファイル・同じエラーで100%失敗）から、問題は一過性の外部要因ではなく、このファイルのフル解像度デコードが決定的に失敗する現象だと判断
- まず元サイズのまま `setScaledSize` を指定するフォールバックを試したが、実際のDCTスケーリングが発生せず無効（素の `read()` と同じ結果）と判明
- `image_cache._load_qimage()` で素の `reader.read()` が失敗した場合、`_FALLBACK_SCALES = (7/8, 1/2, 1/4)` の順に本当に縮小した `setScaledSize` で再読み込みを試す
- それでも失敗したら、`_LAST_RESORT_MAX_SIDE = 384`（`grid_view.THUMB_SIZE` と同じ値。一覧表示でこれまで一度も失敗していない）まで縮小して最終手段とする
- `get_sync()` 側の単純な即時リトライ（同じ処理をもう一度呼ぶだけ）は失敗が決定的である以上無意味と判断し削除

## エラーケース

| 条件 | メッセージ / 挙動 |
|------|------------------|
| スケールデコード・フォールバックも含めて全て（遅延リトライ4回）失敗する | 「画像がありません」を表示したままになる（本当に読み取れない破損ファイル等を想定） |
| 遅延リトライ待ち中にユーザーが別の画像/フォルダに移動する | リトライ結果は無視され、現在表示中の画像には影響しない |
| LRU上限により現在表示中の画像がキャッシュから外れる | 再表示時に `get_sync()` が同期的に再デコードするのみで、ユーザーには見えない |

## 未対応ケース

- サムネイルのディスク永続化キャッシュ
- フォルダツリーの行描画自体の仮想化・遅延生成
- 読み込み中であることを示すプログレスインジケーター
